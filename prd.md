## Section 1 — Product overview (reference)

### What TraceOn is

TraceOn is an MCP (Model Context Protocol) server that Claude Code calls after editing code to verify the change actually works end-to-end. It runs a Playwright test the agent wrote, correlates browser evidence with backend traces and logs via OpenTelemetry, ranks the evidence into a compact packet, and returns a structured `VerificationResult` that the agent reasons over to decide done/iterate/surface.

### The problem it solves

Today, when Claude Code finishes a task, "done" means the code compiles and unit tests (if any) pass. It does not mean the feature actually works end-to-end in a running system. That confirmation requires a human to manually click through the feature, watch logs, and verify behavior.

TraceOn moves that confirmation into the agent's loop automatically. The agent writes implementation and test, calls `traceon_verify`, reads structured evidence about what really happened across services, and iterates if something is wrong.

### The differentiation from Claude Code's `/goal`

`/goal` is a loop runner — it lets Claude Code keep iterating until an evaluator model decides a condition is met. The evaluator reads the conversation transcript only.

TraceOn is an evidence provider — it produces structured runtime evidence the agent can reason over. The evidence comes from the actual runtime (browser + backend services), not from what Claude claims happened.

The two are complementary. Natural workflow: `/goal` keeps the loop going. TraceOn verifies each iteration. The honest pitch is *"Claude has access to real runtime evidence instead of just its own conversation transcript."*

### The target user

Solo developers and small teams using Claude Code on web applications. Specifically those with:

- A frontend that talks to a backend over HTTP
- Backend services they can instrument with OpenTelemetry
- An existing Playwright test setup, or willingness to write one

### Out of scope for v1

- Production environment safety (v3+)
- VS Code extension (v2)
- CI/CD integration (v3)
- Multiple backend connectors (v1 ships with SigNoz only)
- LLM verdict generation inside TraceOn (the agent is the LLM)
- Multiple OS support (Mac OR Linux for v1, not Windows)

## Section 2 — Architectural invariants (reference)

These are decisions that hold across the entire build. If a feature would violate one, the feature changes, not the invariant.

### I1 — One `trace_id` per verification run, propagated via W3C `traceparent`

No custom headers. OpenTelemetry auto-instrumentation handles propagation between services. The trace ID is generated by TraceOn at the start of each run.

### I2 — The ranker is a pure function

`rank(rawEvidence: RawEvidence, config: RankerConfig): RankedPacket`. No I/O, no network calls, no LLM calls. Deterministic — same input always produces same output. Lives in a package with no side-effect dependencies.

### I3 — All data stays on the developer's machine

No cloud services, no telemetry-on-TraceOn-itself, no analytics. Everything runs locally: SigNoz in Docker, SQLite on disk, Playwright as a child process.

### I4 — The MCP server is the only entry point

External tools (Claude Code) invoke TraceOn only through MCP tool calls. No HTTP API, no CLI for v1 (CLI is v1.1+).

### I5 — Redaction runs before evidence leaves the local machine

Even though the MCP server only talks to a local Claude Code instance, redaction always runs. This is a security baseline, not an optimization.

### I6 — TraceOn never edits user code

TraceOn runs tests. It produces evidence. The agent edits code. There is no path in TraceOn that writes to source files.

### I7 — Iteration is the agent's responsibility

The skill (in the user's `.claude/skills/`) defines when to iterate, when to declare done, when to surface to the user. TraceOn is a stateless tool that runs once per call. It has no memory of "this is iteration 2 of 3" beyond storing run history.

## Section 4 — The MCP tool surface (reference)

TraceOn v1 exposes exactly one MCP tool: `traceon_verify`.

### Tool definition

```typescript
{
  name: "traceon_verify",
  description: "Run a Playwright test for a feature change and return ranked runtime evidence. Use this to verify the feature actually works end-to-end after editing code. Pass the test you wrote, the user's intent, and the files you changed.",
  inputSchema: {
    type: "object",
    required: ["test"],
    properties: {
      test: {
        type: "string",
        description: "Path to the Playwright test file to run, relative to the project root"
      },
      intent: {
        type: "string",
        description: "The user's intent in natural language. Used for evidence weighting and surfaces in the result if coverage suggests the intent was not verified."
      },
      changed_files: {
        type: "array",
        items: { type: "string" },
        description: "List of files modified in this iteration (implementation + test). Used for coverage check."
      },
      env: {
        type: "string",
        description: "Environment name from .traceonrc.yaml. Defaults to 'default'."
      },
      prior_run_id: {
        type: "string",
        description: "Optional. The run_id of the previous attempt, if iterating."
      },
      iteration_index: {
        type: "integer",
        description: "Optional. Which iteration this is (1, 2, 3...). Used for skill-side iteration cap."
      }
    }
  }
}
```

### Return type — `VerificationResult`

```typescript
interface VerificationResult {
  run_id: string;           // ULID, TraceOn's identifier
  trace_id: string;         // 32-hex W3C trace ID
  test_status: "passed" | "failed" | "timedOut" | "interrupted";

  test_summary: {
    file: string;
    name: string;
    duration_ms: number;
    steps_executed: string[];
    failure_message?: string;
  };

  evidence_summary: {
    tier1_count: number;
    error_spans: number;
    error_logs: number;
    page_errors: number;
    http_5xx: number;
    http_4xx: number;
    incomplete: boolean;    // true if trace wait timed out
  };

  coverage: {
    hits: string[];         // files in changed_files that had spans
    misses: string[];       // files in changed_files with no spans
    warnings: string[];     // human-readable concerns
  };

  ranked_packet: RankedPacket;

  intent_hint?: {
    relevant_spans: string[]; // span IDs that match intent keywords
    relevant_logs: string[];  // log IDs that match intent keywords
    note?: string;            // e.g., "Test passed but did not exercise caching path"
  };

  evidence_path: string;    // absolute path to evidence directory on disk
}
```

### Error codes the tool can return

| Code | When | Action |
|---|---|---|
| `TEST_FILE_NOT_FOUND` | The `test` path doesn't exist | Agent surfaces to user |
| `PLAYWRIGHT_SPAWN_FAILED` | Playwright child process failed to start | Surface to user |
| `TRACE_BACKEND_UNREACHABLE` | SigNoz API not responding | Surface, instruct user to start SigNoz |
| `RANKER_TIER1_OVERFLOW` | Tier 1 evidence exceeds token budget | Surface — system is on fire |
| `EVIDENCE_DIR_WRITE_FAILED` | Can't write to `.traceon/runs/` | Surface |

import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-http';
import { Resource } from '@opentelemetry/resources';
import { ATTR_SERVICE_NAME } from '@opentelemetry/semantic-conventions';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { BatchLogRecordProcessor, LoggerProvider } from '@opentelemetry/sdk-logs';
import { logs } from '@opentelemetry/api-logs';

const SIGNOZ_OTLP = 'http://localhost:4318';

const sdk = new NodeSDK({
  resource: new Resource({ [ATTR_SERVICE_NAME]: 'traceon-sample-backend' }),
  traceExporter: new OTLPTraceExporter({ url: `${SIGNOZ_OTLP}/v1/traces` }),
  instrumentations: [getNodeAutoInstrumentations()],
});

const loggerProvider = new LoggerProvider();
loggerProvider.addLogRecordProcessor(
  new BatchLogRecordProcessor(new OTLPLogExporter({ url: `${SIGNOZ_OTLP}/v1/logs` }))
);
logs.setGlobalLoggerProvider(loggerProvider);

sdk.start();
console.log('OTel instrumentation started');
```

#### 6.4 Build the frontend

Edit `frontend/src/App.tsx`:

```tsx
import { useState } from 'react';

function App() {
  const [text, setText] = useState('');
  const [summary, setSummary] = useState('');
  const [loading, setLoading] = useState(false);

  async function handleSummarize() {
    setLoading(true);
    try {
      const res = await fetch('http://localhost:3001/api/summarize', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ text }),
      });
      const data = await res.json();
      setSummary(data.summary);
    } finally {
      setLoading(false);
    }
  }

  return (
    <div style={{ maxWidth: 600, margin: '2rem auto', padding: '1rem' }}>
      <h1>Summarizer</h1>
      <textarea
        data-testid="input"
        value={text}
        onChange={(e) => setText(e.target.value)}
        rows={6}
        style={{ width: '100%' }}
      />
      <button
        data-testid="summarize-btn"
        onClick={handleSummarize}
        disabled={loading || !text}
      >
        {loading ? 'Summarizing...' : 'Summarize'}
      </button>
      {summary && (
        <div data-testid="summary" style={{ marginTop: '1rem' }}>
          <strong>Summary:</strong> {summary}
        </div>
      )}
    </div>
  );
}

export default App;
```

import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
} from '@modelcontextprotocol/sdk/types.js';

const server = new Server(
  { name: 'mcp-spike', version: '0.0.1' },
  { capabilities: { tools: {} } }
);

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [{
    name: 'ping',
    description: 'Returns pong. Used to verify MCP connectivity.',
    inputSchema: { type: 'object', properties: {} },
  }],
}));

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  if (request.params.name === 'ping') {
    return { content: [{ type: 'text', text: 'pong' }] };

  throw new Error('Unknown tool');

const transport = new StdioServerTransport();
await server.connect(transport);

## Section 9 — Core types

**Goal:** All the TypeScript types TraceOn uses are defined in `packages/core/src/types.ts`.

**Prerequisites:** Section 8 complete.

**Deliverable:** A single types file that's the source of truth for every data structure in TraceOn.

### Types to define

The complete types file. Type comments are intentional — keep them.

```typescript
// packages/core/src/types.ts

/**
 * Identifiers
 */

/** ULID, e.g. 01HX2K7QF3MNRSGYE4ZW9PVCBA. TraceOn's run identifier. */
export type RunId = string;

/** 32-hex-character W3C trace ID. */
export type TraceId = string;

/** 16-hex-character W3C span ID. */
export type SpanId = string;

/**
 * Raw evidence (output of gather phase, input to ranker)
 */

export interface Span {
  span_id: SpanId;
  parent_span_id?: SpanId;
  trace_id: TraceId;

## Section 10 — The ranker (pure function)

**Goal:** The three-tier ranker exists as a pure function with tests covering all 10 canonical scenarios.

**Prerequisites:** Section 9 complete.

**Deliverable:** `packages/core/src/ranker.ts` and 10 test fixtures in `packages/core/tests/fixtures/`.

### Algorithm specification

The ranker takes `RawEvidence` and produces a `RankedPacket` by:

1. **Compute Tier 1.** For every evidence item, include it as Tier 1 if:
   - It's a span with `status === "ERROR"`
   - It's a log with `level === "error" || level === "fatal"`
   - It's a browser event with `kind === "page_error"`
   - It's a span representing an HTTP response with status code >= 500 (check attribute `http.status_code`)
   - It's the failed test assertion (check `test_summary.status === "failed" || "timedOut"`)

2. **Check budget.** If `estimateTokens(tier1) > budget_total - budget_total * 0.2` (reserve 20% for Tier 2 + scaffold), throw `RANKER_TIER1_OVERFLOW`.

3. **Compute Tier 2 candidates.** Anything that's:
   - A log with `level === "warn"`
   - A span exceeding the per-service p95 duration (compute per-service p95 from all spans in the run)
   - A browser event with `kind === "console" && level === "warn" || "error"`
   - A 1-hop parent or child of any Tier 1 span (lookup via `parent_span_id`)

4. **Sort Tier 2.** By severity: errors > warnings > slow spans > console errors. Within each category, by timestamp ascending.

5. **Greedy-pack Tier 2.** Iterate sorted candidates, add each if it fits in remaining budget. Stop when next item doesn't fit.

6. **Summarize Tier 3.** Everything not in Tier 1 or Tier 2. Produce a string under `tier3_summary_cap` tokens summarizing:
   - Count of info logs grouped by service
   - Count of OK spans
   - Count of successful HTTP requests
   - Any notable patterns (e.g., "many cache misses")

### Token estimation

Use a simple heuristic: `estimateTokens(item) = JSON.stringify(item).length / 4`. Not perfect, but consistent.

```typescript
const REDACT_RULES = [
  { name: 'email', pattern: /[\w.+-]+@[\w-]+\.[\w.-]+/g },
  { name: 'jwt', pattern: /eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+/g },
  { name: 'credit_card', pattern: /\b(?:\d[ -]*?){13,16}\b/g },
  { name: 'aws_key', pattern: /AKIA[0-9A-Z]{16}/g },
  { name: 'generic_secret', pattern: /(?:api[_-]?key|secret|token)["\s:=]+[A-Za-z0-9_-]{20,}/gi },
];

export interface RedactionRecord {
  field_path: string;
  rule: string;
  count: number;
}

export function redactString(s: string, records: RedactionRecord[], fieldPath: string): string {
  let result = s;
  for (const rule of REDACT_RULES) {
    const matches = result.match(rule.pattern);
    if (matches) {
      records.push({ field_path: fieldPath, rule: rule.name, count: matches.length });
      result = result.replace(rule.pattern, `[REDACTED:${rule.name}]`);
    }
  }
  return result;
}

export function redactObject(obj: any, path = '$'): { redacted: any; records: RedactionRecord[] } {
  const records: RedactionRecord[] = [];

  function walk(node: any, currentPath: string): any {
    if (typeof node === 'string') return redactString(node, records, currentPath);
    if (Array.isArray(node)) return node.map((item, i) => walk(item, `${currentPath}[${i}]`));
    if (node && typeof node === 'object') {
      const result: any = {};
      for (const [k, v] of Object.entries(node)) {
        result[k] = walk(v, `${currentPath}.${k}`);
      }
      return result;
    }
    return node;
  }

  return { redacted: walk(obj, path), records };
}

import type { Span, CoverageInfo } from './types.js';

export function computeCoverage(
  spans: Span[],
  changedFiles: string[]
): CoverageInfo {
  const filesWithSpans = new Set<string>();

  for (const span of spans) {
    const filepath = span.attributes['code.filepath'];
    if (typeof filepath === 'string') filesWithSpans.add(filepath);
  }

  const hits: string[] = [];
  const misses: string[] = [];
  const warnings: string[] = [];

  for (const changed of changedFiles) {
    // Skip test files for coverage check
    if (changed.includes('.spec.') || changed.includes('.test.')) continue;

    const hit = [...filesWithSpans].some(f => f.endsWith(changed) || changed.endsWith(f));
    if (hit) hits.push(changed);
    else misses.push(changed);
  }

  // Heuristic: frontend files (tsx/jsx) likely have no backend spans
  for (const miss of misses) {
    if (miss.endsWith('.tsx') || miss.endsWith('.jsx') || miss.endsWith('.vue')) {
      warnings.push(`${miss}: frontend file, 0 spans expected`);
    } else {
      warnings.push(`${miss}: backend file with no spans — change may not be exercised`);
    }
  }

  return { hits, misses, warnings };
}

import { z } from 'zod';
import { spawn } from 'child_process';
import { mkdirSync } from 'fs';
import { resolve } from 'path';
import { generateRunId, generateTraceId } from './ids.js';
import { persistRun } from './persistence.js';
import { rank, SigNozClient, gatherEvidence } from '@traceon/core';
import type { VerificationResult, TestSummary } from '@traceon/core';

export const verifyToolDefinition = {
  name: 'traceon_verify',
  description: 'Run a Playwright test and return ranked runtime evidence. Use after editing code to verify the change works end-to-end.',
  inputSchema: {
    type: 'object',
    required: ['test'],
    properties: {
      test: { type: 'string' },
      intent: { type: 'string' },
      changed_files: { type: 'array', items: { type: 'string' } },
      env: { type: 'string' },
      prior_run_id: { type: 'string' },
      iteration_index: { type: 'integer' },
    },
  },
};

const VerifyArgs = z.object({
  test: z.string(),
  intent: z.string().optional(),
  changed_files: z.array(z.string()).default([]),
  env: z.string().default('default'),
  prior_run_id: z.string().optional(),
  iteration_index: z.number().int().optional(),
});

export async function handleVerify(args: unknown): Promise<VerificationResult> {
  const parsed = VerifyArgs.parse(args);
  const runId = generateRunId();
  const traceId = generateTraceId();
  const evidenceDir = resolve(`.traceon/runs/${runId}`);
  mkdirSync(evidenceDir, { recursive: true });

  // Spawn Playwright
  const testStartMs = Date.now();
  const testResult = await runPlaywright({
    test: parsed.test,
    traceId,
    runId,
    evidenceDir,
  });
  const testEndMs = Date.now();

  // Gather evidence
  const signozClient = new SigNozClient({ baseUrl: 'http://localhost:3301' });
  const rawEvidence = await gatherEvidence({
    runId,
    traceId,
    evidenceDir,
    testSummary: testResult,
    changedFiles: parsed.changed_files,
    intent: parsed.intent,
    signozClient,
    testStartMs,
    testEndMs,
  });

  // Rank
  const rankedPacket = rank(rawEvidence);

  // Persist
  await persistRun({ runId, traceId, status: testResult.status });

  // Construct result
  const result: VerificationResult = {
    run_id: runId,
    trace_id: traceId,
    test_status: testResult.status,
    test_summary: {
      file: parsed.test,
      name: testResult.name,
      duration_ms: testResult.duration_ms,
      steps_executed: testResult.steps_executed,
      failure_message: testResult.failure_message,
    },
    evidence_summary: summarizeEvidence(rawEvidence),
    coverage: rawEvidence.coverage,
    ranked_packet: rankedPacket,
    intent_hint: computeIntentHint(rawEvidence),
    evidence_path: evidenceDir,
  };

  return result;
}

### Playwright spawn

`packages/mcp/src/playwright.ts`:

```typescript
import { spawn } from 'child_process';
import type { TestSummary } from '@traceon/core';

export async function runPlaywright(opts: {
  test: string;
  traceId: string;
  runId: string;
  evidenceDir: string;
}): Promise<TestSummary> {
  return new Promise((resolve) => {
    const startTs = Date.now();
    const child = spawn('npx', ['playwright', 'test', opts.test, '--reporter=json'], {
      env: {
        ...process.env,
        TRACELOOM_TRACE_ID: opts.traceId,
        TRACELOOM_RUN_ID: opts.runId,
        TRACELOOM_EVIDENCE_DIR: opts.evidenceDir,
      },
    });

    let stdout = '';
    child.stdout.on('data', (d) => { stdout += d.toString(); });

    child.on('close', (code) => {
      try {
        const report = JSON.parse(stdout);
        const test = report.suites?.[0]?.specs?.[0]?.tests?.[0]?.results?.[0];
        resolve({
          file: opts.test,
          name: report.suites?.[0]?.specs?.[0]?.title ?? 'unknown',
          status: code === 0 ? 'passed' : (test?.status === 'timedOut' ? 'timedOut' : 'failed'),
          duration_ms: Date.now() - startTs,
          steps_executed: test?.steps?.map((s: any) => s.title) ?? [],
          failure_message: test?.error?.message,
        });
      } catch {
        resolve({
          file: opts.test,
          name: 'unknown',
          status: 'interrupted',
          duration_ms: Date.now() - startTs,
          steps_executed: [],
          failure_message: 'Failed to parse Playwright report',
        });
      }
    });
  });
}
```

### ID generation

`packages/mcp/src/ids.ts`:

```typescript
import { randomBytes } from 'crypto';

// Crockford's base-32 alphabet for ULID
const ALPHABET = '0123456789ABCDEFGHJKMNPQRSTVWXYZ';

export function generateRunId(): string {
  const time = Date.now();
  let timestamp = '';
  let t = time;
  for (let i = 0; i < 10; i++) {
    timestamp = ALPHABET[t % 32] + timestamp;
    t = Math.floor(t / 32);
  }
  const random = randomBytes(10).toString('base64url').slice(0, 16).toUpperCase().replace(/[^0-9A-Z]/g, '0');
  return timestamp + random;
}

export function generateTraceId(): string {
  return randomBytes(16).toString('hex');
}
```

### Skill content

This is the actual skill text. Write it as-is.

```markdown
---
name: traceon-verify
description: Use this skill when implementing new user-facing features, fixing bugs that involve user-facing behavior, or any change where end-to-end verification matters. Trigger words include "add", "implement", "build", "create", "fix bug in", or feature work that crosses frontend and backend.
---

# Verifying changes with TraceOn

You have access to the MCP tool `traceon_verify`. Use it to verify
that your implementation actually works end-to-end, not just that the
code compiles or unit tests pass.

## The workflow

When the user asks for a new feature or behavior change:

### 1. Implement the change

Write the implementation as you normally would. Frontend, backend,
whatever's needed.

### 2. Write a Playwright test

After implementing, write a Playwright test that exercises the feature
end-to-end. The test should:

- Open the relevant UI page
- Perform the user's actions (clicks, form fills, navigation)
- Reach an assertion that confirms the expected behavior
- Use `test.step()` blocks for each user action — this makes the
  evidence TraceOn returns much more readable
- Use stable selectors like `data-testid` rather than CSS classes
- Make real HTTP requests (do NOT mock the backend) — TraceOn needs
  to capture actual backend evidence

Example structure:

```typescript
import { test, expect } from '@traceon/playwright';

test('feature works end to end', async ({ page }) => {
  await test.step('Navigate to feature', async () => {
    await page.goto('/feature');
  });

  await test.step('Perform user action', async () => {
    await page.locator('[data-testid=action-btn]').click();
  });

  await test.step('Verify outcome', async () => {
    await expect(page.locator('[data-testid=outcome]')).toBeVisible();
  });
});
```

### 3. Commit implementation and test together

Use a clear commit message describing the change.

### 4. Call traceon_verify

Pass:

- `test`: the path to the test file you wrote
- `intent`: the user's request, restated in your own words
- `changed_files`: every file you modified (implementation AND test)

### 5. Read the VerificationResult

The result has these key fields:

- `test_status`: passed/failed/timedOut
- `evidence_summary.tier1_count`: count of high-priority evidence
- `coverage`: which changed files had spans (proof they were exercised)
- `ranked_packet`: the actual evidence ranked by importance
- `intent_hint`: notes about whether the test verified the intent

### 6. Decide based on the result

Apply this decision logic:

**DECLARE DONE when all of:**
- `test_status === "passed"`
- `evidence_summary.tier1_count === 0`
- `coverage.warnings.length === 0`
- `evidence_summary.incomplete === false`

**ITERATE when:**
- `test_status === "failed"` and Tier 1 evidence shows a clear cause in your changed code
- Read the Tier 1 evidence carefully, identify the root cause
- Edit the implementation (NOT the test) to fix the issue
- Call `traceon_verify` again, incrementing `iteration_index`
- Maximum 3 iterations — after that, surface to the user

**SURFACE to the user when:**
- `test_status === "passed"` but `coverage.warnings.length > 0`
  - The test passed but didn't really exercise your change
  - Explain the warning and ask whether to update the test
- `test_status === "passed"` but `evidence_summary.incomplete === true`
  - Trace was incomplete; late evidence may have been missed
  - Explain and ask whether to trust the result or investigate
- `test_status === "timedOut"` and `evidence_summary.error_spans === 0`
  - Timeout without an obvious error usually means async behavior
  - Ask the user how the feature should behave (sync vs background)
- Errors are in services or files you didn't change
  - The failure is likely environmental, not a bug in your change
  - Surface the cross-service evidence and ask the user

## What NOT to do

- Do NOT modify the test file during iteration unless the user
  explicitly approves. The test is your specification; changing it
  during fixing invalidates verification.
- Do NOT call `traceon_verify` more than 3 times in a row. After 3
  failed iterations, surface to the user with all the evidence.
- Do NOT declare done if `coverage.warnings` contains warnings about
  backend files. A backend file with no spans usually means your
  change wasn't exercised.
- Do NOT use mocked backend responses in the test. TraceOn needs
  real backend evidence.

## When NOT to use this skill

Skip TraceOn verification for:

- Refactors with no behavior change (existing tests should pass)
- Documentation, comments, formatting
- Build configuration that doesn't affect runtime
- Any change too small to warrant a Playwright test

## Special cases

**Frontend-only changes (no backend involvement):** the coverage
warning will fire for backend files in `changed_files` (there will be
none). That's fine. As long as the test passed and Tier 1 is empty,
declare done.

**Backend-only changes (no UI change):** still requires a Playwright
test that exercises the changed endpoint via the frontend. If the
endpoint isn't reachable from the UI, write a test that calls it
directly.

**New feature with no existing UI:** you may need to add minimal UI
to enable testing. That's fine — implement the UI as part of the
feature work, then the test can exercise it.

## What "evidence" actually means

When you read the `ranked_packet`, Tier 1 contains the highest-signal
items: error spans, error logs, HTTP 500s, page errors, the failed
assertion. These are almost always relevant to the root cause.

Tier 2 contains supporting context: warnings, slow operations,
parent/child spans of Tier 1 items. Useful for understanding why
something went wrong.

Tier 3 is summarized — counts and themes only. Use it to understand
what else happened in the trace without burning tokens on details.

The point: reason from evidence, not from assumption. If Tier 1 shows
"Stripe call timed out at 5s," your fix should address the timeout —
either increase it, or add retry logic, or use a webhook. Don't guess.
