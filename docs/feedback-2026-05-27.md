# User feedback — 2026-05-27 (round 3)

Third-round feedback from the same maintainer dogfooding TraceOn on
Trainery-Frontend + Review-cloud. Comes after v0.0.9 (skill staleness)
and v0.0.10 (doctor) shipped. The doctor worked as designed and caught
the Core API CORS gap on first run. Past that, the maintainer ran real
verifications, hit four new failure modes, and surfaced what would be
the highest-ROI next ship.

## New gotcha — dev server staleness

> First run after re-applying Option C: test failed because Vite's
> federated bundle at :3006 was still serving the rolled-back version
> of the file, even though the new code was on disk and typechecked.
> TraceOn correctly reported "vis-internal-row-employee not found" —
> the signal was right, but the cause wasn't in my code, it was in the
> toolchain. I had to manually grep the file to prove my code was on
> disk before realizing it was an HMR settling issue. One blind rerun
> later, it passed in 4 seconds.
>
> The skill's decision rules cover environment (CORS, missing services,
> infra) but not "your dev server is one rebuild behind your editor."
> That's a real failure mode worth a dedicated rule — something like
> "if a testid that should exist after a file edit doesn't appear,
> check the bundle hash before assuming a code bug."

## Iteration cost is low — that changes how I think

> The retry ran in 4 seconds. That makes "just rerun and see" a
> reasonable strategy instead of frantically debugging. It's a different
> shape than CI loops where every iteration is minutes. For TraceOn to
> work, that fast loop is load-bearing.

## Tier 2 noise is still bad and now I'm sure it's not just me

> Same 17 CORS console errors, repeated verbatim across both runs. The
> budget would be much better spent on "16 CORS errors blocked by
> traceparent allowlist — backend needs to add it to
> Access-Control-Allow-Headers" as one summary line. As it is, every
> Tier 2 read is the same paragraph 17 times. I learned to skim past
> them entirely, which is the opposite of what evidence should do.

## Coverage warning is still wrong for frontend files

> coverage.misses listing my frontend file with coverage.warnings
> saying "frontend file, 0 spans expected" — the tool knows the warning
> is bogus and emits it anyway. Two passes through the skill rules to
> remember that this case is benign. A `tool_thinks_this_is_fine: true`
> field would save the round trip.

## State-drift between sessions is a real failure mode

> Between asking-you-for-the-token and now, the file was rolled back to
> the tile design. TraceOn can't know that and isn't expected to. But
> the failure pattern (test expecting testids that don't exist in the
> file) was the only clue. A first-line `assertCodeContains('vis-internal-row')`
> style check before running the wizard test would have caught this in
> seconds instead of routing through Playwright navigation + 5s timeouts.

## Net read

> Better than last time, but for a structural reason. The actual
> verification (once code, server, and test were aligned) worked
> perfectly — 13/13 functional steps, clean evidence, fast turnaround.
> The friction was all upstream of TraceOn (token, bundle staleness,
> file revert). Which is sort of the point: when TraceOn fires
> correctly, it tells you exactly what the browser saw. When something
> prevents it from firing correctly, you debug your toolchain, not your
> feature.

## Maintainer's prioritised improvements (user's own ranking)

> If you're considering rolling TraceOn out more broadly, the
> highest-ROI improvements would be:
>
> 1. Aggregate repeated console errors in Tier 2
> 2. Suppress coverage warnings for files matching `*.tsx`/frontend
>    patterns instead of just labeling them
> 3. Add a "bundle freshness" probe before tests start (or at least
>    surface it explicitly)
> 4. Fix the `env` parameter so AUTH_TOKEN doesn't need a workaround file
>
> The skill text itself is genuinely good — clearer decision tree than
> most tooling docs. I leaned on it both rounds without confusion. The
> friction is in the runtime, not the instructions.

## Maintainer's response — proposed v0.0.11 bundle

Read of the feedback: accurate, and items 1-3 are real product gaps.
Item 4 (the env parameter) was partially solved in v0.0.7 (`extra_env`
+ `.traceon/auth.json`), so the friction is more about which path the
SKILL.md recommends first.

| # | Drag point | Scope | Where |
|---|---|---|---|
| 1 | **Tier 2 console-error aggregation** | Group duplicate console errors by normalized message, surface as one entry with a count + sample list. The ranker already deduplicates spans; same pattern for browser events. ~1.5h including vitest cases. | [packages/core/src/ranker.ts](../packages/core/src/ranker.ts) |
| 2 | **Suppress frontend "miss" warnings** | When a `changed_files` entry matches a frontend pattern (`.tsx`/`.jsx`/`*/src/components/`/etc.), drop it from `coverage.misses` entirely OR keep the warning but add a `severity: 'info'` flag so the agent's skill can short-circuit. Lean: drop the entry, add a single info-level summary line ("3 frontend files in changed_files — no backend spans expected"). ~1h. | [packages/core/src/coverage.ts](../packages/core/src/coverage.ts) |
| 3a | **Bundle-freshness skill rule** | Add a new SKILL.md decision rule for the dev-server-staleness pattern. The rule pattern: when a testid you just added doesn't appear, do ONE blind retry (cheap — ~4s); if still missing, then suspect the bundle vs. your code. Zero code, all docs. ~20 min. | [skills/traceon-verify/SKILL.md](../skills/traceon-verify/SKILL.md) |
| 3b | **Bundle-freshness probe** (deferred) | A real probe (compare file mtime on disk to served bundle hash) needs to plumb through to the frontend dev server's manifest — Vite-specific, fragile, larger scope. Skip for v0.0.11; revisit if 3a doesn't pay off. | — |
| 4 | **SKILL.md: lead with `extra_env` for one-off auth** | The current auth section recommends `.traceon/auth.json` first (the "set once" path). For the common case (you have a JWT, you're iterating on a single feature), `extra_env` is lower-friction. Reorder so the recommendation is: try `extra_env` first; switch to `.traceon/auth.json` if you're iterating across many sessions. ~15 min docs. | [skills/traceon-verify/SKILL.md](../skills/traceon-verify/SKILL.md) |
| 5 | **State-drift assertion pattern** (user's own suggestion) | Document the `assertCodeContains` pattern in SKILL.md as a recommended first-line check when a test depends on a specific testid added by the code change. The agent already has Read access to source files; this is just calling out the pattern. ~10 min docs. | [skills/traceon-verify/SKILL.md](../skills/traceon-verify/SKILL.md) |

**Total v0.0.11 scope: ~3h.**

### Recommended ship order

1. **#1 (Tier 2 aggregation)** — biggest user-visible improvement; addresses the "17 identical CORS lines" complaint directly.
2. **#2 (frontend coverage)** — addresses the second-most-frequent friction (the "tool thinks this is fine but warns anyway" round trip).
3. **#3a + #4 + #5 (SKILL.md updates)** — three small additions to the skill in one commit. Cheap and they compound (each new rule reduces the chance of the agent getting confused in the future).

### Deferred to v0.0.12+

- **#3b (real bundle-freshness probe)** — needs Vite-specific manifest plumbing. Wait for #3a (the skill rule) to ship first; if "blind retry once" closes the gap in practice, the heavier probe is unnecessary.
- **Multi-backend doctor probe** — round-3 also flagged that `traceon doctor` only checks the first backend it finds. If the user has Core API at `:8000` AND Review-cloud at `:8001`, only one gets probed. Worth ~1h to detect all distinct origins from vite proxy config.

   - (a) `extra_env` → `.traceon/auth.json` → inlined  (lean toward this)
   - (b) `.traceon/auth.json` → `extra_env` → inlined  (current)
3. **Multi-backend doctor probe** worth doing as part of v0.0.11 or punt to v0.0.12?
