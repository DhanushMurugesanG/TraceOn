# v1.1+ candidates

Improvement ideas logged during v0.2.0 implementation, per the "no new
product ideas mid-release" rule. None of these block v0.2.0.

## From the embedded-mode work (2026-06-11)

- **Embedded data-file TTL / `traceon clear-cache`.** v0.2.0 clears
  `~/.traceon/embedded/*.ndjson` at the start of each MCP server session,
  which bounds growth per session but not within a long-lived session with
  many verifies. A size-based rotation or `traceon clear-cache` subcommand
  would close that. (Truncating while the collector holds an append fd is
  POSIX-safe, but restarting the collector at a size threshold is simpler.)
- **Collector version upgrades.** `OTELCOL_VERSION` is pinned (0.154.0).
  Bumping it requires a traceon-cli release. Fine for now; a
  `traceon upgrade-collector` path (or auto-upgrade on init with the old
  binary kept until verified) avoids coupling collector fixes to CLI ships.
- **Port-conflict auto-resolution.** v0.2.0 errors with remediation when
  :4319 is busy. Could instead probe for a free port and rewrite the
  project config + tell the user the new exporter endpoint. Decided
  against for v0.2.0 — silently changing the port the user's backend must
  export to causes more confusion than the error does.
- **Doctor: probe the embedded collector live.** The doctor checks the
  binary is installed; it could also spawn it briefly (or detect a running
  one) and POST a synthetic span end-to-end. Heavier, more conclusive.
- **OTLP logs guidance per language.** Embedded mode carries a logs
  pipeline, but most SDK setups export traces only. Setup snippets for
  OTLP log export (pino/winston → OTLP, Go slog bridge, Python logging
  handler) would make log evidence real for embedded users.
- **Windows support.** The binary manager's platform detection is the only
  hard darwin/linux gate left in embedded mode; otelcol-contrib ships
  windows_amd64 release artifacts. Pairs with the existing "Windows in
  v1.2" plan.
- **gRPC OTLP receiver.** v0.2.0 receives OTLP/HTTP only. The collector
  supports gRPC trivially (one more receiver block in the generated
  config); add when a user's SDK can't do http/protobuf.

## From the v0.2.0 code review (2026-06-16)

- **zod discriminated-union config schema.** `readProjectBackendConfig`
  hand-rolls per-backend `typeof` guards. A `z.discriminatedUnion('backend',
  …)` (verify.ts already depends on zod) would centralize validation and
  give real error messages, scaling better as backends are added. Deferred
  because the `settle` sanitizer already closes the actual validation gap
  this release; this is a structural cleanup, not a bug.
